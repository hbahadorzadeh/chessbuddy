## Context
The publisher explicitly reaffirmed app memory only and requested one running instance for multiplayer. No accounts or confidential profile data are needed. First accepter can claim a seat; the creator can abandon a wrongly claimed game.

## Decisions
- Store bounded game records in a process-global Map shared by bundled API/MCP routes. Atomic synchronous comparisons/writes protect a record version within one process. Store reads return clones. Reject new games at 1,000 active records instead of evicting active games. Sweep expired games every minute and on create/read. No database, Redis, disk persistence or dependencies.
- Random 192-bit base64url bearer codes authenticate seats. Only SHA-256 hashes are stored server-side. The creator chooses a color. Joining atomically closes the public UUID invitation and assigns the other color. No lost-code recovery, email, OAuth or removal of a joined player.
- Invitation links contain only UUIDs. Player codes are passed in POST bodies/tools and private per-game browser/widget state, never in URLs. They may pass through the player's own ChatGPT conversation for natural-language moves. Spectator links contain a separate read-only code in the fragment, removed from the browser address bar when captured. Rotating/revoking spectator access invalidates older codes. Only creator manages sharing.
- Every move validates full history with chess.js, player turn, current move revision and a request UUID. Receipts bind exact actor/revision/input; duplicate successful requests return latest accepted shared state without another move or clock charge. Conflicting reuse fails. Metadata uses a separate version so settings don't invalidate move revisions.
- Keep maximum 400 half-moves as existing prototype. Shared game deadline is seven days after creation, independent of moves, settings, joining, sharing or reads. Memory cleanup and service expiry checks enforce it. Thinking clocks begin when the second player joins; ledger records each committed move.
- UI polls every three seconds while visible, with no background worker or socket. Headless tools update the same record without rendering another board. It never asks ChatGPT to play the human opponent's turn.
- Coaching is per player; explanations strips candidate moves, hints exposes questions/concepts only, suggestions permits legal catalogue/tactical candidates. Spectators get explanations. ChatGPT response adherence must be verified in-host; authored notes are not an engine.
- Replay is local navigation of an immutable completed-game history, with guidance recomputed at requested ply via the same access code and UUID until expiry. Active-game rewind/pause, shared replay cursor, partial-FEN multiplayer starts, and automatic draw claims/resignations are outside this slice.

## Rollout and Risks
The publisher chose to stay on Vercel with best-effort memory and possible missing games. Restart/deploy loses all games. Vercel Functions do not guarantee one shared process; disclose missing-game failures. Do not add Redis, Docker hosting or unverified single-instance configuration. Readiness requires shared API/MCP state verification and separate-user host acceptance. Public links can be forwarded; possession is permission, not identity proof. Browser/ChatGPT storage can be unavailable, so users must retain private codes. Platform logs have their own policies; seven-day app expiry is not a guarantee about provider retention. No account-based fairness or rated play is promised.
